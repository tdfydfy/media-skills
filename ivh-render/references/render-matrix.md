# 出片矩阵与故障排查

## 一、格式由产物决定

`render.mjs` 读产物 HTML 里的 `CONFIG.BG`，自己选编码：

| `CONFIG.BG` | 编码 | 像素格式 | 容器 | 用途 |
|---|---|---|---|---|
| `transparent` | ProRes 4444（`prores_ks -profile:v 4444`） | `yuva444p10le` | `.mov` | 叠到实拍上 |
| `opaque` | H.264（`libx264 -crf 18`） | `yuv420p` | `.mp4` | 直接投放 / 投屏 |

ProRes 4444 是行业默认的带 alpha 中间格式，剪映 / PR / FCP / DaVinci 都直读；
`.webm`（VP9 alpha）的兼容性差得多。
抽帧密度、preset 与两条引擎的取舍见 SKILL 第四节。

---

## 二、假透明的根因

headless 浏览器默认给页面铺不透明白底 —— 截图时必须传
`--default-background-color=00000000`（`shoot.mjs` 已内置，且只在 `BG=transparent` 时才加）。
这一步漏了，出来的就是"alpha 平面全 255"。

判据与复检方式（为什么必须抽 alpha 平面、为什么按时间点抽样）见 SKILL 第五节。

## 三、故障排查

| 现象 | 原因 | 处理 |
|---|---|---|
| `前置检查` 报 `HIDE_HUD 不是 true` | 产物没设 `HIDE_HUD: true` | 改产物 CONFIG 后重跑。这是最快被肉眼发现的低级事故 |
| 前置检查报 `取不到总时长` | `timeline` 的 `data-out` 全是 0，或 `text` 的幕缺 `data-sec` | 补上时间；模板运行时会写 `data-duration` 但以内容为准 |
| 视频只有 1 帧 | 产物没有内容（`.comp` 或 `.scene`），或时间全为 0 | 检查时间轴 / 幕是否真的写了 |
| 成片里组件"闪一下就没" | `data-out - data-in` 太短，或抽帧跨过了整个停留期 | 降低 `--step`，或检查脚本里素材点停留是否 ≥0.8s |
| 找不到 ffmpeg | 未安装或不在 PATH | 设 `IVH_FFMPEG` 指向 `ffmpeg.exe` 全路径 |
| 找不到浏览器 | Edge / Chrome 装在非标准位置 | 设 `IVH_BROWSER` |
| 提示「空档帧实测不是全透明」而跳过了复用 | 空档里其实有东西：`HIDE_HUD` 没关、`BG` 不是 `transparent`、或 `.comp` 之外还有可见元素 | 先修产物；确认没问题再显式关掉复用出片 |
| 渲染比预期慢一个数量级 | 两种 CDP 传输都没连上，走了 cli 回退引擎 | 画面一致，只是慢。耗时按 1.1s/帧 估；先查下面那条 |
| 日志出现「WebSocket 传输不可用」 | 本机安全软件 / 防火墙拦了跨进程回环（特征是 `connect ETIMEDOUT 127.0.0.1:<端口>`，`netstat` 里浏览器明明在 LISTENING） | 不用处理 —— auto 先走管道那条，不受影响 |
| 图片里数字永远是 0 | `?t=` 定位没有冻结计数器 | 产物模板的运行时已处理该逻辑 |
| 数字截出 `+-1%` 这种脏值 | 计数器进度 `k` 没夹到 [0,1]，虚拟时间下 rAF 时间戳可早于采样点 | 模板已夹好（`Math.min(1, ...)` 是必需的） |
| 文件比预期大 | 采样帧率远低于输出帧率，容器在大量重复帧 | 提高采样密度（调小 `--step`）；`--fps` 造不出画面 |
| 加了路数但没变快 | 已经到这台机器的饱和点（见第四节） | 不必再调 —— 物理核吃满了，再加只是多起进程 |

## 四、抽帧耗时模型（实测标定）

`render.mjs` 的耗时预估按这张表算，别凭感觉估。

| 项 | 值 | 口径 |
|---|---|---|
| cdp 单帧（默认） | **0.131s** | 1920×1080 / 软件光栅化 / 单路 / 已开快压 |
| cdp 单帧（`--gpu`） | 约 0.111s | 光栅化只占 5%，GPU 上限就这么大 |
| cli 单帧（回退路径） | 1.1s | 每帧拉起一个浏览器 |
| 逐帧成本里最大的一块 | PNG 编码（91%） | 在浏览器进程内部 —— 管道 / 落盘 / GPU 都碰不到 |

**并行上限**（饱和点跟机器走，两个标定样本）：

| 机器 | 路数 | 墙钟 | 提速 | 吞吐 |
|---|---|---|---|---|
| 笔记本 · 8 逻辑核 / 4 物理核<br>1920×1080 · 374 帧 | 1 | 51s | 1.00× | 7.3 帧/秒 |
| | 3 | 29s | **1.76×** | 12.9 帧/秒 |
| | 6 | 30s | 1.70× | 12.5 帧/秒（已饱和） |
| 台式 i5-14600K · 20 逻辑核 / 14 物理核<br>1080×1440 · 3072 帧实渲染（4105 帧中 1033 帧空档复用） | 6 | 39.4s | 1.00× | 78 帧/秒 |
| | 10 | 28.1s | 1.40× | 109 帧/秒 |
| | 16 | 24.5s | **1.58×** | 123 帧/秒（仍在线性区） |

PNG 编码要的是**物理核**（超线程对 zlib 几乎无效）：4 物理核的笔记本 3 路就吃满了，
14 物理核的台式到 16 路还在涨。所以默认值是分档的 —— **≤8 逻辑核封 3，其余封 16**。
**换机器要重标这两行** —— 物理核数一变，饱和点就变。

> **跨路数不是逐字节相同**（这条以前写错了）。台式上同一产物、同一帧集：
> 6 路 vs 16 路有 90/4105 帧不同，单帧最多 1.57% 的通道值差 1~2 个色阶，PSNR 64 dB ——
> 肉眼是同一帧。但 6 vs 6、16 vs 16 各自 4105/4105 **完全一致**。
> 所以渲染是「**分片布局的确定性函数**」：**同一路数 100% 可复现**（空档复用、串行补抽、
> 重跑都不受影响），跨路数只能算肉眼等价，不能按 MD5 比。原因大概率是每个 worker 是
> 独立浏览器会话，Chrome 的栅格化 / 图层提升会随「这个会话已经渲了多少帧」演化，
> 分片大小不同 → 会话历史不同 → 极少数帧取整差 1~2。

复现：
- **墙钟**：同一产物 `--step 0.5 --workers N` 各跑一次比时间。
- **确定性**：**同一路数**跑两遍，帧目录两两比 MD5（应 100% 相同）；再换个路数跑一遍 ——
  会看到上面那种 1~2 个色阶的差异，这是预期内的。
