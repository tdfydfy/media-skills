# 写脚本（信息图视频 · 第 1 环）

**只干一件事：把文字变成脚本。不碰 HTML、不碰渲染。**

产出物是一份 **`脚本.json`**（+ 一份给人看的同名 `.md`），
交给下游 `ivh-standalone`（独立视频）或 `ivh-overlay`（透明素材）。

```
文稿 / 逐字稿 / SRT + 使用场景
        ↓   ← 你在这里
   脚本.json  ──→ ivh-standalone  ──→ ivh-render
              └─→ ivh-overlay     ──→ ivh-render
```

---

## 零、先问，别猜

开工前必须确认前两项。**默认值在这里是最贵的错误**——判错支线等于全盘重做。

| # | 要问的 | 为什么必须先定 |
|---|---|---|
| 1 | **要做成什么？** 一条独立成片 / 一堆贴到别人画面上的透明素材 | 两条支线的**文本结构完全不同**，没有"两用脚本" |
| 2 | **风格**（六选一，让用户选，不要自己定） | 风格决定字号容字量，写完再换要回头重写字 |
| 3 | 是否有人声口播？（有稿子 vs 我要帮你写稿） | 决定要不要产出 `voiceover[]` |
| 4 | 画布比例、总时长上限 | `standalone` 才要问，`overlay` 恒 3:4 |

**没有逐字稿也能开工**：按 `秒 ≈ 字数 / 4.5` 估时，反向写出一份逐字稿再排结构。
这是第 5 项要问的：只要能拿到时长，就能排脚本。

风格选项：`doodle` 手绘科普 · `riso` 潮流观点 · `blueprint` 技术工程 ·
`minimal` 商务数据 · `neon` 科技发布 · `pixel` 复古趣味。

---

## 一、判定用途（分水岭）

按顺序问，第一个命中的就是答案：

1. "要一条成片发出去" → **`standalone`**
2. "叠在我的口播上 / 剪映里贴上去 / 要透明底" → **`overlay`**
3. "画面铺满整屏，但背景透明叠实拍" → **`standalone` + `bg=transparent`**（不是第三种产物）

判据始终是 **连贯 vs 稀疏**，不是透明与否。完整判定规则见
`references/purpose-routing.md`。

## 二、写脚本

### 两条支线的结构

**`standalone`** —— 幕结构。每幕一个主张，A-roll（画面主张）+ B-roll（证据）分规划。
```
scenes[]  role: open → body → close
              aroll: 标题 或 生成素材
              broll: 数据 / 图表组件
```

**`overlay`** —— 素材点。只挑值得停一眼的地方，每块独立成立。
```
points[]  kind: chapter | concept | data | image
              elements[]: ≤3 个（一组元素 + 它们的关系）
```

### 三层文本，别写混

| 层 | 给谁 | 字数 | 落到哪个字段 |
|---|---|---|---|
| 口播稿 | 听 | 15~40 字/句 | `voiceover[].text` |
| 整屏标题 | 看（最大一行） | **≤2 行 × ≤12 字** | `scenes[].aroll.text` |
| 信息卡 / 提示标签 | 看 | ≤14 字/行；标签 **≤6 字** | `points[].elements[].t` |

**屏幕字念出来不能和口播一样。** 口播给推理，屏幕字给落地数字与关系，两者相加才完整。
详见 `references/two-track-text.md`。

### 提炼：屏幕字不是"概括一下"，是压出来的

屏幕字来自一条压缩链，每一步只做一件事：

```
原文 / 口播稿 → ① 抓手（数字、对比、代价） → ② 论点（带因果的一句）
              → ③ 主张（能不能被反驳？） → ④ 屏幕字（≤2 行 × ≤12 字）
```

**第 ③ 步是分水岭**：「渠道下沉很重要」没人反对，它是共识不是主张；
「一线见顶，增量全在下沉」有人反对，它才是主张。**主张是要付代价的判断。**

每个位置先写 **5 个候选**再挑 1 个（有刻度 > 可反驳 > 短 > 顺口）——
第一个念头永远是最安全的那个，爆发点通常在第 4、5 个候选里。
完整方法、钩子句式、对照表见 `references/distillation.md`。

### 锚点：屏幕字什么时候出现

| 类型 | 时机 |
|---|---|
| 数字 / 结论 | 口播**说完之后** 0.2~0.4s（默认） |
| 结构 / 预告 | 口播**说到之前** 0.3~0.5s |
| 概念 / 名词 | 与口播**同步** |

### 密度

| | `standalone` | `overlay` |
|---|---|---|
| 一屏 / 一块 | 一幕 5~8s | 一点停留 2.5~4.5s |
| 全局节奏 | 每 10s 约 1~2 个组件 | **每 60s 8~12 个素材点** |
| 间隔 | 幕与幕首尾相接、不留缝 | 点与点之间留 **≥1.5s 纯透明空档** |
| 共存 | 允许 A-roll 与 B-roll 同屏 | 同一时刻**只有一组元素** |

一句话记：**`standalone` 是填空，`overlay` 是点缀。**

### 选组件

`comp` 只填**类名**，不写坐标不写样式。15 个组件、按口播信号倒查的选型表，
以及 D3 / Lottie 的升级条件，见 `references/chart-choices.md`。

> 竖版素材优先用 `c-flow`（转化）/ `c-stack`（递进）/ `c-cmp`（对照）这三个竖版原生组件。

## 三、交付：机器校验 + 用户确认

### 1. 先跑机器校验（纯文本，秒级）

```bash
node scripts/check-script.mjs 脚本.json
```

8 条结构硬规则 + 7 组检查：支线二选一、`overlay` 形态锁定、幕区间连续、
`role` 三类齐全、时长对齐、素材点空档、元素数上限、双层文本不重复，
以及第 7 项 **提炼度**（空转标题 / 屏幕字重复 / 名词短语当头标题 → FAIL）。

**不过不许交付。** 下游会先跑这一遍再开工——带病脚本在下游会变成一堆没法改的返工。

完整字段定义见 `references/script-format.md`。

### 2. 然后把脚本交给用户确认

产出是**两份**：`脚本.json`（给下游）+ `脚本.md`（给人看）。
用 `present_files` 把 `.md` 递给用户，**等用户说"可以"再往下游走**。

`.md` 里要有一节 **「候选与选择」**：每个位置列出 5 个候选、标出选了哪个、为什么。
用户一眼就能看出这些字是「挑」出来的还是「想」出来的（见 `distillation.md` 第五节）。

不要跳过这一步直接去做 HTML。脚本判错支线，下游全部返工，这是整条链上最贵的一种错；
而它也是唯一一处"改一行只要几秒"的地方。

> **闸门 1 / 3 —— 文本确认。**
> 闸门 2 是 HTML 效果（下游 ②③ 负责），闸门 3 是出片前（④ 负责）。
> 三道闸门之间，机器只做**读文本**的校验；任何"好不好看"的判断都交给用户。

---

## 四、明确不做什么

- ❌ 不写 HTML、CSS、动画实现 —— 那是 ②③ 的事
- ❌ 不管坐标、落点、避让 —— 下游按画布决定
- ❌ 不渲染、不选编码 —— 那是 ④ 的事
- ❌ 不定色值、不定字体 —— 风格名一交，下游自己取全套变量

**你的边界就是那份 JSON。** 脚本里多写一行"这个卡片放在左边"，
下游就得判断该不该听，这就是耦合的开始。
